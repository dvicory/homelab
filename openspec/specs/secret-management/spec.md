## Requirements
### Requirement: abstract secret request option

A NixOS-level option `secretRequests` SHALL be defined, providing a provider-agnostic interface for services to declare secrets.
Each entry SHALL specify the `sopsFile` (which encrypted file the secret comes from) and `key` (the path within that file).
When `sopsFile` is omitted, it SHALL default to a per-host path derived from `config.networking.hostName` in the provider aspect.

```nix
options.secretRequests = mkOption {
  type = attrsOf (submodule {
    options = {
      sopsFile = mkOption { type = path; };
      key = mkOption { type = str; default = name; };
    };
  });
};
```

#### Scenario: Service declares a per-host secret

- **GIVEN** a service aspect sets `secretRequests."crowdsec/bouncer-api-key" = { }`
- **WHEN** the NixOS configuration is built
- **THEN** `sopsFile` SHALL default to `modules/hosts/${config.networking.hostName}/secrets.yaml`
- **THEN** `key` SHALL default to `"crowdsec/bouncer-api-key"`

#### Scenario: Service declares a shared secret

- **GIVEN** a service aspect sets `secretRequests."crowdsec/enrollment-key" = { sopsFile = ./shared/secrets.yaml; key = "crowdsec/enrollment_key"; }`
- **WHEN** the NixOS configuration is built
- **THEN** the secret SHALL be read from `shared/secrets.yaml` at the specified key

### Requirement: SOPS provider aspect

A SOPS provider aspect SHALL read `config.secretRequests` and map each entry to `config.sops.secrets`.
It SHALL define a `secrets.sopsFile` NixOS option defaulting from `config.networking.hostName`.
This SHALL be the only place that imports `sops-nix` or any `sops` module.

```nix
options.secrets.sopsFile = mkOption {
  type = path;
  default = "modules/hosts/${config.networking.hostName}/secrets.yaml";
};
```

#### Scenario: SOPS provider fulfills requests

- **GIVEN** `secretRequests."myapp/db-password" = { sopsFile = ./host.yaml; key = "myapp/dbPassword"; }`
- **WHEN** the SOPS provider aspect evaluates
- **THEN** `sops.secrets."myapp/db-password"` SHALL be configured with the specified `sopsFile` and `key`

#### Scenario: Multiple providers coexist

- **GIVEN** `secretRequests` contains entries with different providers (e.g. `provider = "sops"` vs `provider = "vault"`)
- **WHEN** each provider aspect evaluates
- **THEN** each provider SHALL only process entries matching its provider type
- **THEN** the final config SHALL merge secret resolutions from all active providers

### Requirement: secret wiring independent of den

The `secretRequests` option and all provider aspects SHALL use standard NixOS modules with `options` and `config`.
No den quirk/policy pipes SHALL be used for secrets.
This SHALL remain functional if the host config is generated by den, clan, or a manual NixOS system call.

#### Scenario: Works outside den pipeline

- **GIVEN** a `nixpkgs.lib.nixosSystem` call that imports the secretRequests option and provider aspects
- **WHEN** the system evaluates
- **THEN** secrets SHALL resolve identically to when generated through den

#### Mechanism

- The SOPS provider aspect SHALL be a static aspect included via `den.default.nixos`
- `options.secretRequests` SHALL be declared inside the SOPS provider's NixOS module
- `secrets.sopsFile` NixOS option SHALL default from `config.networking.hostName`
- No `mkRequester`/`mkProvider` contract functions — `secretRequests` IS the contract
- The existing `modules/flake/sops.nix` (SOPS app wrappers) continues unchanged
